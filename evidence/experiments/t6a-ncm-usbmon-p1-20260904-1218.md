# T6A CDC-NCM usbmon P1 observation — 2026-09-04

## Scope

Read-only USB bus identification and passive observation were performed through
the dedicated raspi4 SSH path. No T6A module, role, IP, descriptor, or USB
binding operation was performed.

The device `2c7c:7006` was identified on raspi4 as USB device `2-1`, bus `2`,
devnum `9`. The permitted wrapper reported `usbmon2` for bus 2.

At observation start raspi4 `usb0` was `192.168.250.2/30`, UP, carrier `1`.
T6A `ncm0` remained `192.168.250.1/30`, UP, carrier `1`, with RX/TX errors 0
after the test.

## Capture and simultaneous P1

Capture file: `/srv/t6a-lab/p1-forward-20260904.pcap`.

- Format: little-endian pcap, `USB_LINUX_MMAPPED`
- Size: 445,624,979 bytes (about 425 MiB)
- USB records: 75,831 for bus 2/device 9 bulk endpoints
- T6A → raspi4 command: `iperf3 -c 192.168.250.2 -t 10`
- Result: 568 MiB, 476 Mbit/s, Retr 0

The wrapper emitted `unexpected EOF while looking for matching \"` after the
capture completed, but the pcap was present and parseable. This is recorded as
a wrapper diagnostic, not as a successful clean wrapper exit.

## usbmon results

Endpoint `8 IN` (T6A → raspi4):

- 29,085 submits; every observed submit request length was 16,384 bytes.
- 28,715 completes were observed.
- Complete data lengths were mainly 15,224 bytes (25,615) and 14,528 bytes
  (3,052); 13,832 bytes occurred 38 times.
- No zero-length IN data completion was observed.
- Completion interval median was about 150 µs; p95 about 634 µs. Large gaps
  exist at capture boundaries and during startup/teardown.
- The submit/complete event stream shows a host outstanding level reaching the
  64-request region; exact steady-state count is boundary-affected because the
  capture begins and ends with requests already in flight.

NCM parsing of IN completion payloads found an `NCMH` NTB and NDP entries in
28,715/28,715 completions. Datagram counts were:

- 10 datagrams: 28,708 NTBs
- 2 datagrams: 3 NTBs
- 1, 3, 6, and 8 datagrams: one NTB each

Thus NDP aggregation is active under this load. The 16 KiB value is a request
buffer/upper bound, while actual NTB block lengths cluster below the limit
(15,224 and 14,528 bytes).

Endpoint `5 OUT` (host → T6A) was mostly 524-byte receive requests. OUT
completion records carry no captured payload in this usbmon format; they do not
by themselves indicate ZLP. No IN ZLP was observed. The non-1024-multiple IN
completions are short-ending transfers, but usbmon alone does not prove whether
each resulted from a protocol-level short packet versus completion framing.

## Capture-free reproduction

To separate usbmon overhead from the link condition, a second unchanged P1 was
run without capture immediately afterward:

- Result: 566 MiB, 474 Mbit/s, Retr 0
- raspi4 `usb0`: UP, `192.168.250.2/30`, carrier 1
- T6A `ncm0`: UP, `192.168.250.1/30`, carrier 1, RX/TX errors 0

Therefore the 476 Mbit/s result is reproducible in the immediate current
state and is not caused solely by usbmon capture overhead. It is not comparable
as a clean bMaxBurst=15 P1 because the final read-only descriptor check showed
SuperSpeed but `bMaxBurst=0` on the displayed 1024-byte bulk endpoints. No
attempt was made to restore bMaxBurst=15, since that would change the current
condition without a separate authorized experiment.

## Priority update

1. First resolve or explain the unexpected current bMaxBurst state before any
   bMaxBurst-dependent comparison. Do not repeat the prior bMaxBurst=15 test
   until the descriptor is again verified as 15 by an authorized method.
2. Under the captured load, 16 KiB host request size is confirmed, NDP
   aggregation is confirmed, and the host supplies many outstanding requests;
   “single host request only” and “no NDP aggregation” are downgraded.
3. The below-limit NTB lengths and stable 10-datagram aggregation keep
   gadget aggregation/flush policy and host aggregation as leading questions.
4. MTU3 QMU/GPD ring starvation is lower priority than data-path processing,
   lock/queue serialization, and DMA/memcpy, but usbmon cannot distinguish
   those internally.

No further condition-changing experiment was performed after detecting the
descriptor mismatch. The large pcap remains on raspi4 under the permitted
`/srv/t6a-lab/` path.
